Reading the table:

- **Task success.** Compact is the only mode in which (a) finishes: Off and Shadow both hit the provider's
  window on call 9. Every other item succeeds in every mode, so on this corpus compaction changes the
  outcome only where the raw history would overflow.
- **Context reduction.** Peak request size drops 14–19 % in the single-checkpoint items (2,102 → 1,764;
  2,360 → 1,928; 2,384 → 2,046) and stays under 2,050 across all 41 calls of (a); total prompt tokens drop
  8–14 %.
- **Total cost including compaction is higher, not lower.** Compact costs 24 % more than Off in (b)
  (11,964 vs 9,616 µ$), 22 % more in (c), 30 % in (f), 35 % in (k). Two effects, both measured: each summary
  call is 300 µ$ (50 prompt + 10 completion tokens at the corpus rates) and the checkpoint envelope
  rewrites the cached prefix, so the cache-hit ratio falls by 12–29 points and cache-read tokens (0.3 $/M)
  are re-billed as input (3 $/M). On a 2,400-token window the reduction cannot pay for the rewrite. See
  §7 for what this means for the defaults.
- **Latency** is wall-clock on the generating machine and is reported, never asserted; the summary
  latency column is 0 because the mock summariser returns synchronously.
- **Prompt-cache effects** are the cache-hit column; Shadow matches Off exactly because it never rewrites
  the request.
- **(l)** never compacts: an unknown window gives `Skipped(capacity_unknown)` on all four passes and cost
  is `Unavailable`; the loop still finishes. **(m)** compacts and reports `Partial` cost in every mode.

## 3. Zero-tolerance invariants (AC 4)

Every one of the 39 rows reports `0 / 0 / 0 / 0` for invalid tool pairs, protected-state loss,
unauthorised cross-thread reads and raw-history loss. The evaluator derives each from the persisted rows,
the provider's request log and the store call log, independently of the loop's own validator:

- *Invalid pairs*: calls without results or results without calls in every provider request (root and
  children) and in the persisted rows; plus, in every mode, no checkpoint boundary (Shadow included) falls
  between a call row and its result row.
- *Protected-state loss*: on every activated checkpoint the current instruction equals the human rows of
  the checkpoint's run at or below the boundary; every quote is the persisted row verbatim; tasks equal the
  board's ids; agents equal the roster; recovery is clean; the index is contiguous to the boundary; the
  summarised artifact is carried; and (Compact only) every instruction, decision and artifact the
  summariser returned is on an activated manifest.
- *Cross-thread reads*: a recording store decorator logs every `(threadId, op)`; each loop only ever read
  its own thread (root reads `corpus-root`, children read `subagent-{id}`).
- *Raw-history loss*: sequence numbers have no gaps and every row a checkpoint covers is still present.

Scenario-specific proofs live in `CompactionCorpusTests.AssertScenarioSpecifics`: (c) the checkpoint
carries all three agents with one `running`; (d) the child compacts and the root does not; (g)/(h) the
parked call builds no provider request, the run that arrives meanwhile is refused with "still deferred",
and the resumption reaches the provider (`AssertParkedRunBuiltNoRequest`); (i) the first request after
restart carries the envelope; (j) the recall tool round-trips; (k) the first append backfills Seq on the
five legacy rows before any cut; (l) `capacity_unknown`.

## 4. Mutation proof (AC 5, spec §12.3)

Each mutation was applied to `src/`, the test project was built, and the compaction fixtures were run (`CompactionCorpusTests`,
`CompactionRolloutTests`, `CheckpointValidatorTests`, `CutSelectorTests`, `CompactionPolicyTests`,
`ManifestAssemblerTests`, `CompactionLoopTests`, `CheckpointPipelineTests`), restored the file with
`git checkout --` and re-checked that the original text was back (`restored`). A green row is a finding,
not a pass.

Twenty-three mutations cover the ten protected classes the spec names, each as a *drop* (the class never
reaches the manifest) and, where a validator rule guards the class, a *bypass* (the drop plus the rule
that would catch it, so the corpus has to catch it on its own). Nineteen went red on the first pass. Four
went green, and each green named something real:

- **M13 (Recovery, forge clean)** — `Recovery = cut.Recovery` could be replaced with a fresh, all-zero
  `RecoveryStateAtCut` and nothing failed. `CutSelector.Select` returns a cut only when recovery is clean
  (its own doc comment says so: all zero for the cut `Select` returns), so no fixture could tell the copy
  from a constant. Fixed by pinning the assembler's contract directly:
  `ManifestAssemblerTests.Recovery_IsCopiedFromTheCut_NotRecomputedAsClean` assembles from a hand-built
  cut whose recovery carries deferred, parked, owed and interrupted counts.
- **M16 (tool pairing, `Splits` never true)** — `IsGenerationBoundary` already refuses a cut inside a
  same-generation call/result pair, so the pairing rule was redundant in every existing fixture. It is
  *not* redundant for a call row whose result never arrived: that row ends its generation, the boundary
  rule accepts it, and only `ToolPairing.Splits` refuses it. Fixed by
  `CutSelectorTests.R1_CallRowWhoseResultNeverArrived_IsNeverTheCut` (interrupted stream, then a later
  run continues the thread).
- **M19 and M22 (loop wiring: `LiveDeferredCount` and `OwedContinuations` forced to 0)** — not fixed, and
  not fixable at the loop level. `MultiTurnAgentLoop` refuses to build a request at all while any
  deferred placeholder is in the messages (`MultiTurnAgentLoop.cs`, "Cannot send request: tool call … is
  still deferred"), and a deferral parks the run before the next policy pass, so the policy is never
  consulted with a live deferral. Corpus (g) and (h) show the refusal rather than a skip, which is why
  `MustSkipWith unsafe_state` could not be asserted for them. Policy row 3 itself is proven by M17 and
  M21; what remains unproven is that the loop would report the counts if that guard ever stopped firing.
  Removing either lambda is therefore safe only while the guard holds — treat both as defence in depth,
  not as covered behaviour.

M13, M16 and M20 were re-run against the new fixtures; the table marks those three rows. M20 had been
red on one fixture only, and for the wrong reason — `Observe_CountsDeferredAndParkedRows_ByTool` counted
one deferred call and one parked wait, which reads 1/1 whichever counter each branch increments — so the
thread it counts is now asymmetric (two deferred, one wait) and the fixture catches the swap itself.

## 6. Rollout controls (AC 7, AC 8)

- **Canary per route** — `Canary_ModeByRoute_EnablesCompactionOnTheNamedRouteOnly` (five cases): with
  global `Mode = Off` and `ModeByRoute["corpus/model"] = Compact` only that route compacts; a model-only
  key matches the model on any provider; an exact key lowers a global `Compact` to `Off` for one route.
- **Kill switches** — `KillSwitch_SkipsEveryDecisionDisabled_AndWritesNoCheckpoint` (config `KillSwitch`,
  env `LMMULTITURN_COMPACTION_DISABLED=1`, and `=true`): every decision is `Skipped(disabled)`, no
  checkpoint row, no state change; the raw request goes out. `CompactionLoopTests` (#684) covers the
  Active → RolledBack transition on the next request after a kill.
- **Rollback** — `Rollback_FeatureOff_SendsTheRawHistory_AndKeepsTheCheckpointAndAuditRows`: phase 1
  compacts (one active checkpoint); phase 2 restarts with `compaction: null` and the next request is the
  raw history — no envelope, and no `CompactionCheckpointMessage` row in it — while the checkpoint row,
  the `compaction.state` projection and the context observation are all still in the store; phase 3
  turns the feature back on and the loop re-adopts the same checkpoint id. Phase 2 found a real defect
  (F1 below).

## 7. Findings

- **F1 (fixed, `MultiTurnAgentBase.GetMessagesWithSystemPrompt`).** With compaction off the raw request
  carried the persisted `CompactionCheckpointMessage` row: it rendered as ~150 tokens of envelope text on
  the mock provider and would be rejected outright by the OpenAI converter (`ChatCompletionRequest`
  throws on an unknown message type). Rollback now reads the raw history without checkpoint rows.
- **F2 (documented).** A legacy run that holds several human rows is R4-protected (injected correction)
  and, when the cut candidate falls inside it, the selector answers `no_safe_boundary`. Corpus (k) gives
  each legacy turn its own run id, which is what the old binary did.
- **F3 (design consequence).** The economic band (policy row 6) never fires on this corpus: predicted
  savings use `CheckpointTokenCap` (6,000) as the summary's output tokens, so at a 2,400-token window the
  prediction is always negative and every compaction happens at the hard band. At a 200k window with
  ~100k tokens removed the same formula is positive (≈ +0.17 $ per checkpoint at the corpus rates), so the
  band is reachable in production but unmeasured here.
- **F4 (documented).** The runtime's estimate runs ~30 tokens above the provider's for the same request
  (joined tool composites are counted split). At a 2,400-token window this is enough for a skipped attempt
  at call 8 to refuse the request (`overflow_after_compaction`); the rollout tests use 2,500.
- **F5 (economics, §2).** On every item that fits the window, Compact costs 22–35 % more than Off because
  the envelope invalidates the cached prefix and each summary is billed. Compaction earns its cost only
  when the alternative is failure (a).
- **Observation.** `run-ledger entries 0` on every row: the corpus loop does not populate the run ledger
  the report reads. Not asserted; worth a look when the ledger is wired for compaction.

## 8. Recommended defaults (AC 9)

Keep `CompactionMode.Off` as the default and roll out per route (`ModeByRoute`) through Warn → Shadow →
Compact; the kill switches and the rollback path are proven above. On the observed results:

- **Ratios 0.70 / 0.80 / 0.90 and target 0.45** behaved as designed: warn one turn before the compact
  band, one skipped economic pass, hard band one turn before overflow, and a 14–19 % peak reduction after
  a cut. No observation argues for moving them.
- **`ReserveMarginTokens` 2,048** could not be exercised at a 2,400-token window (corpus uses 0). F4
  says the estimate skews high by ~1 %, so the reserve is not eating into that margin.
- **`ExpectedFutureGenerations` 3** and `MinPredictedSavingsMicros` 0 are still hypotheses: the economic
  band is unreachable on the corpus (F3). Until a production-window measurement exists, expect every
  pre-emptive compaction to come from the hard band.
- **`MaxCompactionsPerRun` 2**: (a) needed 20 checkpoints across 41 calls in one run at the corpus scale
  (20 turns per window). At production windows a run compacts far less often, but a tool-heavy run that
  is 3× the window would hit the cap and then overflow; the cap is a death-spiral guard, so raise it only
  with `CooldownNewTokens` in place.
- **Residual outcome/cost risk.** F5: on conversations that would have fitted, Compact is a cost increase
  (22–35 % here) and a cache-hit drop, with no outcome gain; the outcome gain is confined to conversations
  that would otherwise fail. Shadow mode is free (identical cost and cache to Off) and reports what
  Compact would have done, so it is the right canary state.

## 9. Not covered

- No live provider, no real tokenizer: every number is the corpus estimator's and the mock provider's.
- The "older binary reads a newer checkpoint row" rollback (§8.3) is covered by the resilient converter's
  unit behaviour, not by running two binaries.
- Latency is reported only.
- **The loop's two cut-blocking lambdas (M19, M22) have no failing fixture.** The request-build guard
  refuses to send while anything is deferred, so `LiveDeferredCount` and `OwedContinuations` never reach
  the policy non-zero through the loop. Policy row 3 and the selector are proven directly (M17, M21, M23);
  the wiring between them and the loop is not. This criterion of §12.3 is unmet for those two lambdas, and
  the report says so rather than weakening the mutation.
