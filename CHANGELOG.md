## [Unreleased]

### Added

- **CodeReviewDaemon.Sample**: DeveloperLearnings phases 1 and 2 — the per-developer learnings subtree, under `Agents/DeveloperLearnings/`. Phase 1 is the arithmetic and the model contract: `DeveloperObservation` (the immutable per-PR ledger record), `DeveloperIdentity.SlugifyAuthor` (author → path segment, as an allowlist so `../../.git/hooks/x` is unconstructible rather than filtered), `DeveloperLearningsLedger` (Laplace-smoothed per-PR `Rate`, `LuckProbability = (1-Rate)^CleanStreak`, `PatternState` classification, cohort-drop `SuppressedDimensions`), and `ClassificationValidator`. Phase 2 is the projection and the four pure formatters: `DeveloperLearningsView` and `DeveloperLearningsRenderer`. Three contracts a later phase codes against:
  - **The model classifies; the daemon counts.** Nothing in the ledger reads model output. The classifier's only contribution is a `patternId` per finding, validated against a known set before it arrives, so the worst a bad classification can do is attribute a real finding to the wrong pattern — never invent a number. `ClassificationValidator` enforces this in code rather than in prompt wording, and rejects a reply **whole** rather than per item: a model that stated a fact the daemon owns has misunderstood its contract, and the classifications it produced in the same breath are not more trustworthy for having parsed.
  - **Streaks are counted in exposed PRs, never in days or in all PRs.** A pattern can only recur where its dimension ran. Measuring in calendar time means a developer's record improves when the reviewer gets narrower or when they ship less, which is the opposite of what the number claims to show. `PatternState.Unjudgeable` is kept separate from `Resolved` for the same reason — a developer who stopped writing that kind of code has not improved.
  - **Renderers cannot re-derive a state.** A renderer handed an impossible input (`Resolved` at luck 0.90) still renders it under `Resolved`. Every state decision lives in the ledger, so the two can never disagree.
  **Not yet wired.** Phases 1+2 have no production caller: every type is `internal`, no config key exists, nothing is written to disk, and no daemon path reaches them — nothing renders under anyone's name on any configuration. Phase 3 carries the wiring. (#547)

- **LmEval**: New `AchieveAi.LmDotnetTools.LmEval` package (`net8.0`/`net9.0`, depending on LmCore and LmMultiTurn only so the harness stays a leaf reachable from both the review daemon and LmWorkflow without a cycle) — the shared judge harness: deterministic gates (`JsonSchemaGate`, `LengthBoundsGate`, `RequiredAnchorGate` over `GateBase`), a rubric-scoring `RubricJudge` against a versioned, validated `Rubric`, a two-family `JudgePanel` with a tie-break arbiter (`TieBreakRules`), `WeightedMeanAggregator`, and the run/compare surface (`EvalRunner`, `EvalRun`, `EvalBaseline`, `BaselineComparer`, `ICorpusReader`/`CorpusPage`/`CorpusSnapshot`). Three contracts are load-bearing for anyone consuming it:
  - **A quantity that was never measured is null, never zero.** `EvalRun.InconclusiveGateRate` is `double?` and stays `null` when no gate ran at all, because a gate outage and a run with no inconclusive gates are opposite facts and `0.0` reads as the good one. Comparison refusals that depend on it (`ComparisonRefusal`) are skipped rather than satisfied when it is null.
  - **A corpus window is stated per call, not held by the reader.** `ICorpusReader.LoadAsync(corpusId, afterCursor, limit, ct)` answers with a `CorpusPage` carrying the snapshot (`null`, not empty, when the window held nothing), the cursor the window *reached* (not the id of the last row it kept, so a window whose every row was rejected still advances), and `Truncated`. **A page that filled its limit and happened to reach the end of the history is not truncated** — an implementation must distinguish the two rather than infer truncation from the row count, or every caller that resumes on `Truncated` loops for ever on the last page.
  - **`EvalBaseline.From` refuses its source run on the same bounds the baseline will impose.** A run whose judges faulted past `maxFaultRate`, whose gates were inconclusive past `maxInconclusiveGateRate`, or whose coverage fell below `minCoverage` cannot be frozen as the number every later run is compared against — the refusal uses the parameters being stored, so the bound refused against and the bound imposed can never drift apart. Ordering mirrors `BaselineComparer.Refuse` exactly: faults, then gate outage, then coverage, then scored-nothing. (#427, #441)

- **Sandbox**: New `AchieveAi.LmDotnetTools.Sandbox` package (`net8.0`/`net9.0`, no ASP.NET/provider dependencies) — a credential-scoped `SandboxClient` for the sandbox gateway's control plane: authenticated create/get/list/delete lifecycle, marketplace preview, and session discovery; command execution (`ExecuteAsync`) over the gateway's direct operations API (`POST`/`GET .../operations`, with gateway-owned exact-byte stdout/stderr artifacts downloaded through the files API) — idempotency/recovery is gateway-scoped (a same-operation-id resubmit is answered from the gateway's retained state) and NOT durable across a gateway restart; and exact UTF-8 file transfer over the direct files/directories API (`ReadTextFileAsync`/`WriteTextFileAsync` = `GET`/`PUT .../files/{mount_id}`, `ListDirectoryAsync` = paginated `GET .../directories/{mount_id}`). Ships with owned or borrowed `HttpClient` transport, stable `SandboxErrorKind`/`SandboxException` error classification, secret-redacted `SandboxClientOptions`, and an `AUTH_ENFORCE=true` live-gateway contract CI job. (#187, #188, #189, #190, #197)
- **Sandbox**: `SandboxClient.DeleteOperationAsync(sessionId, operationId, ct)` — new public surface wrapping the gateway's `DELETE /api/v1/sandboxes/{session_id}/operations/{operation_id}` (ADR 0031 §5), so a long-lived sandbox can bound its artifact footprint without deleting itself. Every `ExecuteAsync` leaves `.mcp-gateway/operations/<operation_id>/<generation>/{stdout,stderr}` in the caller's writable workspace, and the gateway's reaper prunes the terminal **in-memory record only** — the files persist for the sandbox's lifetime. Until now the only cleanup reachable through the SDK was `DeleteAsync`, i.e. tearing the whole sandbox down; that remains the bulk cleanup and is unchanged. Three contract points a caller codes against:
  - **It is not cancellation.** A still-RUNNING operation is refused with `409 operation_running` → `SandboxErrorKind.Conflict` carrying `ErrorCode == "operation_running"`. Branch on the **error code**, not the kind: `idempotency_conflict` and `target_locked` are also `Conflict` and, unlike this one, are not cleared by waiting.
  - **It is not idempotent.** `204 No Content` for a record removed; a uniform `404 operation_not_found` → `SandboxErrorKind.NotFound` for one the gateway does not hold — an already-deleted operation, a TTL-pruned record, a record dropped by a gateway restart, and an id that never existed are all the same answer (the no-existence-oracle boundary, pinned against a never-existent control in the live-contract job rather than assumed). Best-effort cleanup should read `NotFound` as "nothing left to reclaim".
  - **Delete promptly.** Because the reaper drops records without touching files, an operation whose record has already expired by TTL can no longer be deleted through this route at all, and its artifacts then live until the sandbox does. (#464)

- **LmWorkflow**: `StartWorkflow`/`CheckWorkflow`/`WaitWorkflow` agent-facing tools (`StartWorkflowToolProvider`) that launch a pre-authored `WorkflowDefinition` on an isolated controller loop via the new `WorkflowManager`, with bounded concurrency and proactive completion notifications (`NotifyKinds.WorkflowCompletion`). (#179)
- **LmStreaming.Sample (ClientApp)**: conversation sharing is reachable from the UI. #303 shipped the three share routes (`GET`/`POST`/`DELETE /api/conversations/{threadId}/shares`) and no client for them, so the feature existed and could not be used. A share modal in the chat header lists, adds and revokes grants. No client-visible DTO says whether the caller may share, so the UI attempts the action and renders the server's own refusal code — a grantee, a tenant admin, an app-only caller and a published conversation each get their specific reason, and `sharing_unavailable` (enforcement off) disables the add control rather than withdrawing it, because that is a fact about the deployment and not about the caller. A `404` renders a message that does not confirm the conversation exists. (#375)
- **LmMultiTurn**: `TriggerDisposal.DisposeAfter(Task, CancellationTokenSource)` — the deferred-CTS-dispose an `IArmedTrigger` needs because its `DisposeAsync` must not await its own background task (disposal is typically invoked from a continuation of that very task, so awaiting it deadlocks). Five trigger sources each carried a byte-identical copy of the `ContinueWith` + swallow-`ObjectDisposedException` block; they now share one, and an external `ITriggerSource` implementer no longer has to rediscover the shape. (#161)
- **LmMultiTurn**: `SubAgentOptions.NonInheritedToolNames` to exclude specific tools from sub-agent inheritance, and a public `MultiTurnAgentLoop.RegisteredToolNames` accessor.
- **LmMultiTurn**: `IInputAcceptanceObserver` and `IAcceptanceReportingAgent` — an agent can now announce, from the two places a receipt id is minted (`SendAsync` and `TrySendAsync`), that it has accepted an input, and withdraw the announcement if the enqueue is refused. `MultiTurnAgentBase` implements `IAcceptanceReportingAgent` and gained a public `InputAcceptanceObserver` property; both additions are source-compatible. `OnInputAccepted` returns `bool`: `false` means the observer positively knows the reporting agent is not the one it holds for that conversation, and the agent must then refuse the enqueue and fail the send with the new `InputAcceptanceRefusedException` (nothing queued, durable record rolled back). Not knowing is **not** a refusal — an observer holding nothing for the conversation returns `true`. A throwing observer likewise **fails the send with nothing queued** — deliberately, because the alternative is the input sitting in the channel with the host believing the agent idle, which is the exact state this exists to prevent. The interface lives in LmMultiTurn rather than in the hosting assembly so that a host in a *dependent* assembly can be the observer, which is what lets an accept taken inside LmMultiTurn reach a host it cannot reference. (#434)
- **LmMultiTurn**: Per-turn sub-agent spawn suppression — `UserInput.SuppressSubAgentSpawning` asks the run that consumes the input to withhold the `Agent` tool (contract hidden, handler refuses with `spawn_suppressed`), and `MultiTurnAgentLoop` latches it for the whole run, including a run resumed after a deferred tool call and after a host restart (the marker is persisted in thread metadata). Hosts discover the capability through `ISpawnSuppressingAgent` (which now also exposes `EnforcesSpawnSuppression`, so a host can refuse *before* enqueuing) and read `SendReceipt.SpawningSuppressed` as an enforcement statement to fail closed on.
- **LmCore (Identity) — a capability seam on `IResourceAccessPolicy` (adds an interface member; source-breaking for external implementers).** New `EvaluateCapabilityAsync(principal, resource, action, GrantRole? suppliedGrant, ct)` answers the same rights table (spec 7.4.1) as `EvaluateAsync`, but as a display-time PROBE rather than an access attempt, with two differences that follow from that: it writes **no** audit record, and it performs **no** grant I/O — the grantee grant of step 3 is supplied by the caller (resolved once for a whole page) instead of re-queried. It exists because a conversation listing computes `canShare` per row (#482): through `EvaluateAsync` an admin page load wrote one Security/Warning deny per row an operator could not tell from a real refused attempt, and re-queried grants once per row (a 1+N). The attempt seam and its audit are unchanged, so a genuinely refused `Share` still writes exactly one record. In `LmStreaming.Sample`, `ConversationsController.List` now computes `canShare` through the new `ConversationAuthorizer.MayShareForListingAsync`, which routes to this seam — so an admin List writes zero attempt-grade audit records for the capability computation and fetches grants once per page rather than once per row. (#487)
- **Docs**: Four review-daemon ADRs ported from `daemon/review-reliability-and-pr-coverage` — `0015-model-classifies-daemon-counts` (no number, date, state or path in a daemon-rendered artifact may originate from the model; the model classifies, the daemon counts), `0016-developer-learnings-append-only-ledger` (immutable per-PR observations, model-written prose, regenerated views, nothing ever moved or deleted), `0017-resolution-from-absence-over-exposed-prs` (rates measured in exposed PRs, Laplace-smoothed, with an `Unjudgeable` bucket and a cohort-drift guard) and `0018-feedback-to-producer-not-judge` (improvement feedback goes to the coding agent, never to the reviewer, because a primed reviewer measures its own instructions). They were authored as 0012–0015 on that branch and renumbered on the way in — `main` had allocated 0012–0014 meanwhile — rather than taking the slug-identity collision ADR 0010 permits. Each carries a status note stating how much of it `main` implements today: 0015's repository-wide rule is live in `ReviewFindingReconciler`; 0016 describes an unbuilt subtree; 0017 splits — the exposure seam it names (`ReviewSubAgentNode.Template`/`.Status`, the settled roster behind `AwaitSubAgentSettlementAsync`) is live and exercised, while none of the arithmetic that would consume it as exposure is written; and 0018 records a removal (`ReviewFeedbackAgent`, `PrependDeveloperFeedbackAsync`) that has not yet happened. So none of the four reads as a description of code that is not there. Citations that did not resolve from `main` were corrected on the way in rather than carried: the reconciler commit is cited by its `main` sha `448dfaa0` (#539, #560) instead of its sha on the source branch, and the four records' sole "Related" reference — a `scratchPad/` working file that was never committed, `scratchPad/*` being git-ignored — is replaced by issue and PR references that resolve, with each status note recording the substitution. `docs/adrs/README.md`'s index also gains the row for `0014-host-directory-wipe-accepted-residuals`, which was merged without one. (#553)
- **LmMultiTurn (tests)**: a regression test for the property `MultiTurnAgentBase._replayLock` actually exists to provide — that registering a subscriber and snapshotting the in-flight run's replay buffer happen as ONE atomic step against a concurrent publisher's buffer-append + subscriber-snapshot. The existing concurrency test drives a single subscriber, which cannot enter the few-instruction window between the two; the new one puts 32 subscribers against a publisher taking and releasing the lock without pause, and asserts an exact invariant (every canonical message of the run exactly once per subscriber — a replay prefix and a live suffix that meet with no overlap and no gap) rather than a statistical one. It guards one of the two relocations reliably: moving the registration to BEFORE the lock fails it on every run, because the subscriber is then registered for the whole of its lock wait and a message published during that wait is both buffered and sent live, so the replay hands it over twice. The opposite move — registration to just after the lock — loses a message rather than duplicating one, but is only probabilistically caught (measured red once in eleven runs): its window is the few instructions between releasing the lock and writing the registration rather than a whole lock wait, orders of magnitude narrower, and narrower still against a slower agent's lower publish rate. This test is not a guard against that direction. The overlap is constructed rather than hoped for — `PublishToAllAsync` completes synchronously, so a thread-pool publisher runs its whole burst before any queued subscriber is scheduled and every registration meets an idle lock; each subscriber therefore gets a dedicated thread and is parked on a gate the publisher opens as its first act. The test also counts how many subscribers registered mid-burst and fails when that is zero, so a future scheduling change cannot quietly turn it back into a run that proves nothing. Production code is unchanged — the lock was already correct; the guard against regressing it was missing. (#107, #548)

### Changed

- **Misc (source- and binary-breaking) — `TaskManager`'s eleven `[Function]` tools return `FunctionResult` instead of `string`.** A domain failure such as `"Error: Task 999 not found."` now reaches the model with `IsError = true` and a lower_snake_case error code (`task_not_found`, `invalid_args`, `invalid_task_id`, `invalid_status`, `note_index_out_of_range`) rather than as a successful tool result; successes stay unmarked. Only `Text` is serialized, so the JSON on the wire and the `string` the contract advertises are both unchanged — what changes is the flag beside them. The id-typed overloads and `ManageNotes` changed with them; a caller that used a returned string directly reads `.Text` (`GetMarkdown()` still returns `string`). `FunctionResult` shipped in #515 with no production consumer; this is its first. (#521)

- **LmTestUtils (binary-breaking) — the xUnit-coupled logging helpers moved to a new `AchieveAi.LmDotnetTools.LmTestUtils.Xunit` package.** `LoggingTestBase`, `TestLoggingConfiguration`, `TestLoggingFixture` and `TestLoggingModuleInitializer` are no longer in `AchieveAi.LmDotnetTools.LmTestUtils` (they were public in 1.0.33). Namespaces are unchanged, so migration is adding one `PackageReference` — no `using` or source edits. **Upgrade both packages together:** a new `LmTestUtils.Xunit` alongside `LmTestUtils` ≤ 1.0.33 puts the same four types in two assemblies and every use of them fails to compile with CS0433 (ambiguous reference). The move exists because `LmTestUtils` is referenced by applications, not just tests — `LmStreaming.Sample` and `MockProviderHost` both use its `TestMode` SSE responders — so its `xunit` reference put xunit.abstractions, xunit.assert, xunit.core, xunit.execution.dotnet and Serilog.Sinks.XUnit into the chat host's Release publish. It also made the host *require* them to boot: `Serilog.Enrichers.CallerInfo` walks the reference graph of every `AchieveAi.*` assembly and eagerly `Assembly.Load`s it, so merely excluding the files at pack time crashed startup with `FileNotFoundException: xunit.core`. `LmTestUtils` now has no `xunit` and no `Serilog` reference at all. (#520)

- **LmMultiTurn (source- and binary-breaking) — `IConversationStore.ListThreadsAsync` takes a `ConversationListOptions?` before its `CancellationToken`.** Both overloads changed: `(int, int, CancellationToken)` is now `(int, int, ConversationListOptions?, CancellationToken)`, and the scoped one gained the parameter in the same position. `null` means what the old signature did — no exclusion, last-used order — so a call that names its token (`ct:`) or omits it is unaffected; a call that passes the token **positionally** as the third argument no longer compiles, and every external implementer of the interface must update its signature. This was taken as a break rather than papered over with a compatibility overload: an overload restoring the old shape is ambiguous with the new one at every call that relies on the defaults, and the parameter belongs next to the `limit`/`offset` it constrains rather than after the token.
  **Why the parameter exists:** listing is a filter, not a loop. The conversation sidebar asked the store for a page and only then dropped agent-owned (`subagent-*`/`workflow-*`) rows from it. Because `LastUpdated` is bumped by every completed run and background agent runs are constant, those rows crowd the front of a `last_updated DESC` ordering: on a live deployment of 302 threads, 256 of them agent-owned, a 50-row page came back holding 45 agent-owned rows and 5 real conversations, and every older conversation was unreachable behind a page boundary that could never be crossed. Nothing had been deleted. The exclusion and the sort now run inside the store, while it still holds the whole candidate set. `ConversationListOptions` is deliberately kept apart from `ConversationListScope` — one is a presentation predicate derived from the query, the other an authorization predicate derived from the principal, and folding them together would let a caller widen the second by asking for the first. `SqliteConversationStore` **refuses** `ConversationSortOrder.Created` with `NotSupportedException` rather than approximating it in SQL: there is no `created_at` column, and the creation instant lives only in the thread id. (#458)

- **LmMultiTurn / LmStreaming.Sample (behaviour) — a provisioned thread id now carries its creation timestamp.** `POST /api/conversations` minted `thread-{guid:N}`, which `ConversationListOptions.CreationTimestampOf` cannot parse, so the `created` ordering silently fell back to the mutable `LastUpdated` for every conversation the app made — the exact key that ordering exists to avoid. Ids are now minted as `thread-{epochMillis}-{guid:N}`. Conversations provisioned before this keep the old shape and still fall back; the fallback is retained deliberately rather than dropping rows it cannot order. (#458)

- **LmAgentInfra (breaking) — a pooled agent must now report its own input acceptances.** `MultiTurnAgentPool` refuses at creation any agent that does not implement `IAcceptanceReportingAgent`: the factory's result is disposed (along with the resources the pool took ownership of for it) and an `InvalidOperationException` naming the offending type is thrown to the caller that asked for the agent. `AddOutstandingInput`/`RemoveOutstandingInput` narrowed from `public` to `private` as the consequence — an external "record an accept no agent made" entry point can wedge a thread busy for the full 30-second grace with no run able to retire it, and there is no longer any legitimate caller. The four synchronous host call sites (`ConversationsController`, `ChatWebSocketManager`, `ContextDiscoveryInjector`, `WorkflowCompletionNotifier`) are gone with it.
  **Why fail closed rather than keep the host sites as a fallback:** they were never a fallback. Those four covered four of the seven accept paths; the three that #434 exists for (a sub-agent relaying a descendant's question, a sub-agent completion, a peer collaboration message) are taken inside LmMultiTurn and cannot reach the pool from there. A non-reporting pooled agent was therefore already unprotected on exactly the paths hardest to notice, while the retained sites made it look covered. Pooling is the one moment the condition is detectable, so it is refused there, loudly, instead of silently degrading at handoff time. Any `IMultiTurnAgent` derived from `MultiTurnAgentBase` already satisfies this; a hand-rolled implementation must declare `IAcceptanceReportingAgent` and report from every accept path. (#442)

- **LmAgentInfra / LmMultiTurn (behaviour) — a send that races an agent replacement now fails instead of losing the turn.** Reporting an accept and enqueuing it are two steps, and `MultiTurnAgentPool` does its bookkeeping under the same per-thread lock a mode/provider switch holds — so a report could be parked there while the conversation's agent was replaced underneath it. The pool then saw a stale agent and recorded nothing, but the reporting agent's own channel was still open, so the enqueue that followed **succeeded**: the turn sat in an agent being torn down, in no ledger, with its sender holding a `202` for it. The pool now REFUSES that report (`OnInputAccepted` → `false`) instead of ignoring it, and the agent fails the send with `InputAcceptanceRefusedException` having queued nothing. Both host transports translate it as the retryable condition it is rather than as a fault: `POST /api/conversations/{threadId}/messages` answers `503 agent_replaced` (distinct from `queue_full`, which means the opposite about whether retrying the same agent can work) and releases its admission; the chat socket sends the same `agent_released` frame it already sends for the two earlier arrivals of the same handoff, so the client reconnects and retries. (#442)

- **LmAgentInfra (binary-signature change; source-compatible)**: `SandboxSessionRegistry`'s public constructor gained an optional trailing `TimeProvider? timeProvider = null`, so the liveness-freshness window can be driven by a test clock. Source callers using the existing arguments are unaffected, but compiled callers should recompile against this release.
  **Behaviour**: a session is no longer re-probed on the gateway for every acquisition. A probe that confirms a session alive opens a 30-second window during which the next acquisition trusts that answer and issues no round-trip — the probe looks for idle eviction, which takes the gateway minutes, so within the window the answer is already known. Failure semantics are unchanged: a probe that finds the session gone still invalidates and recreates immediately, and a session is stamped only by a genuine gateway confirmation — never by its own creation, and never by the probe's "assume alive" degradation. The window's cost is bounded: if the gateway restarts inside it, the caller sees the failure at first use rather than as a clean recreate, exactly as it would today for a gateway that died right after a probe. (#93)
- **LmMultiTurn (binary-signature change; source-compatible)**: `FileConversationStore`'s public constructor gained an optional trailing `TimeProvider? timeProvider = null`, so the admission-record settle budget can be driven by a test clock. Source callers using the existing argument are unaffected, but compiled callers should recompile against this release.
  **Behaviour**: that settle budget widened from 500 ms to 10 s. It bounds three waits on one admission record — a reader waiting for a record that exists but is not yet readable, a losing reservation re-attempting its exclusive create, and `TryRecordOutcomeAsync`/`TryReleaseAcceptanceAsync` standing down from a mutation gate another mutation still holds — so a contended completion or retraction that previously reported "not mine" after half a second now waits up to twenty times longer before doing so. The widening is deliberate: the threshold separates "a live writer has not finished" from "a dead host left a half-written record", and any fixed value there is decided by scheduler starvation rather than by the store, so the margin has to sit far outside any plausible stall. The cost is bounded to a record that genuinely never settles, which is a fault either way.
  A reservation is also written differently: the payload is serialized before the exclusive create and written by a straight line of synchronous unbuffered syscalls, and the claim is held `FileShare.None` rather than `FileShare.Read`. The record is therefore never observable between the create that arbitrates it and the content that completes it — previously it was flushed from a thread-pool continuation and could be opened, empty, across a scheduling point, which is what made a loaded runner report `IOException` for an input that had been admitted normally. Arbitration is unchanged and remains `FileMode.CreateNew`. (#443)
- **LmMultiTurn (behaviour) — a sub-agent that asked a question no longer settles its caller with `"(no text response)"`.** Resolving an `AskUserQuestion` empties the loop's live deferred-call registry, which is the same registry the sub-agent monitor probed to decide whether a run completion was terminal. A completion landing between the resolution and the answer-derived run's own text was therefore read as genuinely terminal and settled the caller's one-shot latch with the `"(no text response)"` placeholder, silently discarding the real answer. The monitor now latches the parking from the deferred placeholder on its message stream — which is published identically for every provider and cannot be erased by the answer arriving — and keeps such a run non-terminal so the real result can settle it. Two completions can be held this way per question: the run that asked it (whose own completion can be classified after the answer already landed) and at most one following run that never reached the model. Anything else stays terminal, so a sub-agent whose final turn legitimately produces no text still completes rather than holding its caller and its concurrency permit forever. (#262)
- **LmAgentInfra (source-breaking for external implementers)**: `IWorkspaceFileBrowser` gained a fifth member, `ResolveThreadWorkspaceSessionForBackgroundAsync(string threadId, string persistedWorkspaceId, CancellationToken ct = default)`. It is abstract with no default implementation, so any type outside this repository that implements the interface must add it to compile against this release; consumers that only *call* the interface are unaffected. It resolves a thread to its workspace session exactly as `ResolveThreadWorkspaceSessionAsync` does except that it performs no cross-actor provenance comparison, because in-process background work has no caller to compare — presenting `null` there was read as a foreign claim, which silently denied every transcript flush for an S2S-created conversation. **Do not call it from a request-handling path**: a route that reached it would hand any caller the owner's session. It grants no new reach of its own — the gateway call underneath uses the binding's stored credential either way. (#253, ADR 0013)
- **LmMultiTurn (binary-signature change; source-compatible)**: `SendReceipt` gained a fourth positional parameter, `bool SpawningSuppressed = false`. Source callers using the existing three arguments are unaffected, but the generated `Deconstruct` now has four parameters and compiled callers that positionally deconstruct a `SendReceipt` (or bind its primary constructor) must be recompiled against this release. `MultiTurnAgentBase.EnforcesSpawnSuppression` widened from `protected` to `public` for the same reason a host needs it: the capability has to be checkable before an input is queued.
- **LmWorkflow (breaking)**: renamed the `StartWorkflow` agent-facing tool to `StartWorkflowAgent` (`StartWorkflowToolProvider.StartWorkflowToolName`) and sharpened its description to foreground the agent-dispatch framing, so models more reliably choose it over performing the work inline. `CheckWorkflow`/`WaitWorkflow` are unchanged.
- **LmMultiTurn (behaviour) — delayed tool results now resolve as child runs.** A tool result arriving after its run ended previously resumed a single tracked "last deferring run", which collapsed several results into one resume and lost the attribution of which result caused what. Each resolution now gets its own child run caused by the real `ToolCallResultMessage`, never a fabricated user message.
  **Intentional timing, which can read as a missing response:** only the child run that clears the *last* outstanding tool call calls the provider. A request carries the whole history, and a single unfilled placeholder anywhere in it makes that request invalid — so sibling children complete with **zero model turns** and the `awaiting_sibling_results` outcome rather than pretending they finished the work. A caller resolving one of several outstanding calls should therefore expect a completed run with no model output; that is the contract, not a dropped response. (#227, ADR 0004)
- **LmMultiTurn — `ResolveToolCallAsync` behaviour on a store failure.** Resolution is three-phase under one lock (claim, durable write, commit) and the **durable write comes first**, so a store failure leaves the call genuinely unresolved and safe to retry unchanged; the previous ordering could leave an already-mutated history behind a failed write. `ResolveToolCallAsync` keeps its throwing shape and its exact messages. New `TryResolveToolCallAsync` reports the same operation as a `ResolveToolCallOutcome` value instead — `Resolved`/`Duplicate` are success, `NotFound`/`Conflict` are permanent rejections, and `StoreFailed`/`Cancelled` left the call untouched and are safe to redeliver — because the question a webhook receiver actually has is "can I redeliver this?", which an exception does not answer.
  Two defects the rewrite exposed are also fixed: the claimed path applied resolutions unconditionally, overwriting an already-resolved result instead of refusing it; and a history placeholder with no reservation was unresolvable, which is now adopted rather than left wedged.
- **LmAgentInfra (behaviour) — the pool's accepted-input ledger now covers accepts taken inside LmMultiTurn.** `MultiTurnAgentPool` implements `IInputAcceptanceObserver` and attaches itself to every base-derived agent it creates, so a turn accepted by the sub-agent relay, by a sub-agent reporting to its parent, or by a peer's collaboration message holds the entry the same way a transport-initiated send does. - **CodeReviewDaemon.Sample — collect-only is now a capability, not a request, and refusals are recorded.** `EnableCommentPosting=false` meant the daemon *declined to call* its publishers; the HTTP client those publishers hold was fully write-capable the whole time, because `PolicyEnforcedHttpClientFactory` built every per-repo `OperationPolicy` through `DaemonOperationPolicy.BuildForRun` without saying anything about write capability and that parameter defaulted to `true`. Nothing in the code read as a grant, and nothing surfaced the disagreement between what a run declared and what it could do. Three changes, in the order they matter: (1) the factory now passes `allowWriteOperations: EnableCommentPosting`, so on a collect-only run every provider client the daemon constructs structurally refuses `POST`/`PUT`/`PATCH`/`DELETE` against the provider API — a code path that reaches a publisher anyway (a new caller, a resumed stage, a mis-evaluated `shouldPost`) is denied at the seam and has its credential stripped, rather than succeeding. (2) `OperationPolicy.Decide` gained a pre-dispatch **method** gate that refuses any mutating verb on a provider-API operation when the policy has no write capability, so a write arriving under a *read* classification is refused on what it would have done rather than on what it claimed; it is scoped to the API operations because git transport legitimately `POST`s, and the unclassified case is treated as API-addressing so an operation added later makes the gate fire rather than stand down. (3) `allowWriteOperations` now defaults to **`false`** on both `BuildForRun` and the `OperationPolicy` constructor — a write-capable policy has to be asked for by name, which is what stops the next construction site repeating this. Recording never throws and enforcement never consults it: a store failure degrades to "the refusal held but was not written down", never to "the write went through". A companion `ReviewSpawnGate` on the sub-agent settlement barrier refuses and records posting-capable sub-agent templates on a collect-only run — an audit control, not an egress one, since the S2S review host owns spawning. - **LmStreaming.Sample — the `file_tail` trigger forwarded credentials and PII into model context verbatim.** The method that processed a matched line before delivery was called `Redact`, but all it did was escape `<`/`>` and cap length — envelope-boundary defense, which is a different job and no privacy guarantee at all. - **CodeReviewDaemon.Sample (behaviour) — slot hygiene stops re-cloning a store over the repository's own eol attributes, and stops reading a lost probe answer as a clean tree.** Both were live on `main`, and both come out of the one gate at the end of `SlotHygiene.EnsureCleanAsync`, which read a single `git status --porcelain` through `string.IsNullOrWhiteSpace`. The reading is now in a new `Workspace/Git/WorktreeStatusProbe`, whose parsing half is pure and directly testable.
  - **A path whose bytes already ARE the recorded blob is not contamination.** A repository can commit a blob whose line endings contradict its own `.gitattributes` — `text eol=crlf` against a blob that already holds CRLF is the common shape. Git then maps the worktree copy to LF through the clean filter on every comparison, finds it unequal to the CRLF blob, and reports the path modified on a checkout nothing has touched. Measured on WeveNova: one `ServiceConfig.ini`, all 91 of its 91 lines "changed", surviving `reset --hard`, `checkout --force` and `clean -ffdx` alike, because no operation that writes the worktree can produce bytes the clean filter maps back onto that blob. The gate condemned the slot, the re-clone reproduced the identical condition, and the next lease condemned it again — permanently, for every review of that repository. A surviving ` M` path is now classified by the identity of its RAW bytes (`rev-parse :<path>` against `hash-object --no-filters`, which bypasses the filter): equal to the index blob means the file is the committed content whatever `status` says. A real edit changes those bytes and so changes that hash, so the tolerance cannot be widened into "ignore modified files" — everything else (untracked, deleted, staged, renamed, unmerged) stays a leftover, and a probe that could not run leaves its path a leftover too (`GitAnswer.Unknown` is not `No`). Bounded at 25 dirty paths, above which the tree is wrong in bulk and is refused without paying two git invocations per path to say so.
  - **An empty answer is no longer an answer.** The probe now runs `--porcelain -b -z`. `-b` makes a successful probe SAY so: without it a clean tree answers the empty string, which is byte-for-byte what a probe whose output was lost produces — and this daemon has measured a git command exiting 0 with its stdout gone. The old predicate read that failure as cleanliness and handed the store to the next review. `-z` is what makes the paths usable: porcelain v1 quotes any path holding a space or a non-ASCII byte, and a quoted path never matches the index entry the blob lookup asks about. The parser skips the `-b` header, which is load-bearing rather than tidy: the daemon keeps the store DETACHED, so git answers `## HEAD (no branch)`, which without the skip reads as a leftover at code `##` on every single run.
  - **A probe that did not answer gets a verdict of its own.** New `HygieneVerdict.ProbeUnanswered` (and `SlotProbeUnansweredException` out of `ReviewSlotPreparer`) for a probe that failed or whose output did not arrive. It is deliberately neither neighbour: not `NeedsReclone`, which would spend the daemon's most expensive recovery on a question that was never put, and not `Clean`, which is the fail-open being closed. The slot is RELEASED to the pool untouched and the next lease re-probes it; nothing re-clones and nothing retires it. It is charged to the retry budget (`PrOrchestrator.IsGovernedFailure`) for the reason the other slot-preparation failures are — since nothing catches it, a probe that loses its output on every attempt would otherwise busy-loop a stage that can never make progress. On the retry side (`ShouldForceResetAgain`) a non-answer fails CLOSED and buys a second reset pass, while a tree reporting only normalized paths does not: that is precisely the deterministic condition no repeated reset can settle. - **CodeReviewDaemon.Sample (behaviour) — a first-ever review may no longer answer "No new findings since the last review.", and the rate at which it happens is now measured on every start.** The sentence is a claim ABOUT AN EARLIER REVIEW, and a run with no earlier review cannot make it. The daemon made it 57 times: of 116 first-ever primary rounds in the live store, 57 came back as nothing but that sentence — 51 with no prior run on the PR at all, and 6 whose only prior runs were parked at `Discovered` or `ContextReady`. Each took the sentinel exit on turn 1, never fanned out to a sub-agent, and was filed as a completed review of a PR nobody had reviewed. `IsNoNewFindingsSentinel` already *recognised* the text — it decided where the text went, which is not a control — and all 57 walked past it. Two mechanisms now, on production paths, tested to go red when either is removed:
  - **The guard.** `DaemonReviewStageExecutor` asks the store, at the point of use and **before** the artifact write, whether an earlier PRIMARY round on this PR persisted a review BODY (new `ReviewStore.GetPriorReviewPayloads`). If not, the run fails with the new `SentinelUnauthorizedException` rather than persisting the claim — a guard that threw after persisting would already have shipped it to everything that reads the artifact later. The question is deliberately not "has this PR been seen before?": a run discovered and then dead leaves a `review_run` row and no review, so a **row is not a review**; a blank body is not a review; and a prior **sentinel** is not a review either, because a chain of sentinels bottoms out nowhere and the store already holds 58 such bodies for the exact runs this refuses to let re-authorize themselves next round. A genuine re-review whose predecessor reported real findings is still entitled to the exit, and still persists it.
    - **The refusal is charged to the retry budget** — `PrOrchestrator.IsGovernedFailure` now names `SentinelUnauthorizedException` in its `Reviewed` arm, alongside the barrier deadline, the corrupt checkpoint and the host-contract skew. It is the reason the exception has its own type. The prior-review question is answered from the store, so the next poll asks the same question of the same rows and refuses identically — and each attempt is a full review, fanned out and billed, discarded at the last line. Ungoverned, a refused run is written `RetryPending` and re-attempted on **every poll**; that loop would open for every PR whose only prior primary body is one of the 58 historical sentinels. What governance buys is the cadence, not permanent silence: the poll path parks the run once its budget is spent, and `StrandedRunReconciler` then resumes it on the `StrandedRunRetryPendingGraceMinutes` grace timer (45 by default) via `PrOrchestrator.ReconcileAsync` — which is `RunAsync(admitParked: true)` and **resets the governor** for that run id — so the refusal is re-attempted once per reconciler pass and refused identically. That reset is not a leak to plug: it is also the only path by which a run parked for a since-resolved reason recovers without an operator. So the measured win is roughly one wasted review per 45 minutes instead of one per poll, and the recovery path is what the remainder pays for. The park itself is keyed on the run id and never re-evaluated, so a genuine earlier review appearing does not unpark this run; what ends the refusals is the next round, a new run id whose store question now finds a real prior body. A restart also clears the park, as the operator's documented "retry everything" gesture.
    - **The guard reads the sentinel as a whole body, not as a prefix.** `IsNoNewFindingsSentinel` is a `StartsWith("No new findings")` match and stays one — its existing consumers only withhold a comment, where a false positive is cheap. The guard is not in that position, because it discards the review unrecoverably for the round, so it additionally requires the trimmed body to fit within 120 characters (the two mandated sentences are 38 and 34). A substantive first review opening *"No new findings in the auth path, but three Must-fix items below…"* is persisted, not thrown away; and, on the other side of the same predicate, such a body counts as the earlier review a later sentinel may point at.
  - **The standing check.** `PrPollingService` reports the first-review sentinel rate once per start through `ReviewProgressReporter.FirstReviewSentinelRate` — the one logger category the console keeps at Information, so the line is one an operator actually sees. Only each PR's FIRST review counts (`ReviewStore.GetFirstReviewPayloadsSince`, `MIN(artifact id)` per `(repo, PR)`), because a later round's sentinel is legitimate and an alarm inflated by healthy re-review traffic is tuned out inside a week. **Zero is reported too**, so "nobody looked" cannot masquerade as "nothing wrong"; only a non-zero count logs at Warning. The measurement is best-effort — a detector that could take the poll loop down with it would be worse than the blind spot it closes.
  New `CodeReviewDaemon:FirstReviewSentinelLookbackDays` (default 7, `<= 0` falls back to the default) sets the window; `GetFirstReviewPayloadsSince` takes the cutoff as a `DateTimeOffset`, so the `"O"`-shaped rendering that makes `created_at` comparable lives beside the writer, as it does for `ListStrandedRuns`/`ListRetryPendingRuns`. - **LmMultiTurn (behaviour) — one corrupt persisted record no longer aborts a sub-agent restart.** `MultiTurnAgentBase.RecoverAsync` converted the whole persisted batch in a single `FromPersistedMessages` call, so the first undeserializable row threw `JsonException` and lost every record. The two restore sites disagreed on the consequence: `RunAsync`'s startup recovery wrapped the call and degraded to empty history, but `SubAgentManager.RestartRunAsync` called it bare — its enclosing `catch` is teardown-and-rethrow and nothing outward absorbs a store fault — so a single corrupt record aborted the entire restart and stranded a sub-agent the directory still advertised. Recovery now degrades **per-record**: it skips a row that fails to deserialize, logs the skip with the record id, and restores every healthy sibling. Both sites recover through this one method, so they now survive a corrupt store identically, and healthy history is preserved rather than discarded wholesale. A total store IO fault (the load itself throwing) is unchanged — it still propagates, and the restart still leaves the sub-agent restartable.
  Three consequences of degrading per-record are handled explicitly, because a partial restore is a shape the old all-or-nothing conversion could never produce:
  - **A restored history never holds half a tool exchange — whatever caused the half.** A tool call and its result are SEPARATE persisted rows, and a history holding one without the other is rejected by every provider, with nothing downstream repairing it (`RestoreHistory` is a bare `AddRange`, `GetMessagesWithSystemPrompt` returns history unfiltered, and `MessageTransformationMiddleware` passes an unpaired half through verbatim). Two independent routes produce that shape, and both are deterministic, so the thread stays wedged across process restarts instead of recovering on the next attempt. The **write-side** route pre-dates this change and is the likelier of the two: `PersistMessageAsync` appends one row at a time and *swallows* an append failure, so a lost tool-result append leaves a dangling `tool_use` in the store for ever. The **read-side** route arrives with the per-record skip above: the row that fails to deserialize is the partner of a row that does not. Recovery now sweeps the restored set back to the pairing invariant the write path otherwise maintains (`MultiTurnAgentLoop` suppresses persisting a wrap-up tool call for precisely this reason) — a call whose result is missing and a result whose call is missing are both dropped, iterating to a fixed point because one message may carry several call ids. **The sweep is deliberately blind to which route caused the orphan** — it asks only whether a partner is present — so one mechanism closes both, and it therefore runs unconditionally rather than only when a record was skipped, which would leave the older write-side orphan unrepaired. Both persisted call shapes are handled: the singular `ToolCallMessage` production writes (`MessageTransformationMiddleware` splits plural into one-per-call upstream of the turn body) and the plural `ToolsCallMessage` that still reaches the store through the middleware's unsplit passthrough and through the sibling Claude/Codex/Copilot loops. A message carrying no tool call id on either side takes no part in pairing and is always kept — it cannot be matched either way, and a verdict there would delete history on a guess — and duplicate results for one call are kept, because pairing asks whether a partner exists, not how many.
  - **`RecoverAsync` returns `false` when nothing was restored.** The zero-row branch already answered `false` for that same observable outcome; an all-corrupt load now agrees instead of returning `true` for an empty history.
  - **The summary line states what was lost, not just what survived.** It reports restored / attempted / unreadable / unpaired (the three drop-counts partition the attempted total exactly) and is raised to `Warning` whenever anything was dropped, so "recovered 1 record" out of 10,001 is not something an operator has to reconstruct by correlating 10,000 preceding warnings. A record whose `$type` this binary does not recognise — written by a NEWER binary, i.e. a rollback window rather than bit rot — is now reported on its own distinct line: `IMessageJsonConverter` throws the new `UnknownMessageTypeDiscriminatorException` (a `JsonException` subclass, so existing handlers are unaffected). The recovery outcome for such a row is unchanged: skipped, siblings restored. (#489)

## [1.0.33] - 2026-05-23

### Added

- Copilot CLI: project `--disable-mcp-server` / `--disable-builtin-mcps` from `CopilotSdkOptions` (#60)

### Fixed

- **LmAgentInfra (security; new public API) — the lifecycle control plane no longer accepts a signed-in human as an app.** `LifecycleSubscriptionsController` and `LifecycleApprovalController` derived the caller's app id from `ClaimTypes.NameIdentifier`, falling back to `Identity.Name`. A JWT bearer handler with inbound claim mapping on puts a human token's `sub` on exactly that claim, so **any signed-in user could register a lifecycle callback and be handed a signing secret**, filed as an owner under their own subject id — and could settle another app's pending approvals. Both now read the new `LifecycleAppIdentity.AppIdClaimType` claim (`lm_lifecycle_app_id`) and **nothing else**: no fallback, so "the request is authenticated" is no longer the operative rule at those endpoints; "the principal carries the app-id claim" is. The guarantee is the single stamping site, not anything about tokens: a claim's contents are whatever the handler reading a token is configured to map, so a handler told to map a claim of this name would put it on the principal. This repository maps none inbound and mints it in exactly one place — `PrincipalFactory.ToClaimsPrincipalOrNull`, downstream of having established the caller is an app — so nothing a caller presents populates it here. **A host that populates `HttpContext.User` itself must stamp this claim or its app callers will be refused.** (#433)
- **LmStreaming.Sample (security) — the WebSocket transports were a login wall, not an authorization check.** `/ws` and `/ws/subagent` established *who* the caller was (#342) and owned the pooled agent they created (#399), but never asked `ConversationAuthorizer` whether that caller may open *this* conversation. Any signed-in principal in the deployment could name another user's `threadId` and get an agent primed on their transcript, frozen to themselves as owner; `/ws/subagent` threaded no principal at all and replayed `subagent-{agentId}` straight out of the store. Both now resolve through the new `WebSocketConversationGate`, which calls the same `AuthorizeAsync` the REST routes call, **before the handshake is accepted** — `/ws` for `Write` (the socket accepts turns and takes ownership), `/ws/subagent` for `Read` on the parent plus a check of the child against the durable parent link. An existence-hiding refusal is a `404` byte-identical to the REST surface's `unknown_thread`; a child whose provenance does not check out — a row naming a different parent, or no metadata row at all — is admitted but loses its persisted replay, so it answers exactly as an agent id that names nothing. (A missing row is not evidence that nothing was persisted: messages are written during a run and metadata only at completion, so a child killed mid-run keeps a transcript and no row permanently.) `auth/{providerId}` no longer renders the host operator's account, scopes or token expiry to an anonymous caller. **Operational:** with `Identity:Enforce=true` the socket now refuses a `threadId` with no metadata row, so a client must provision through `POST /api/conversations` first — the bundled SPA does not yet do this (#435). With enforcement off, nothing changes. (#419)
- Copilot CLI: route MCP servers via `--additional-mcp-config` file instead of inline args (#61)
- Copilot CLI: trim disabled MCP server names in `BuildCliArguments`

## Version Update Instructions

To update the version for all packages:

1. **Edit Directory.Build.props** and update only these values:

   ```xml
   <MajorVersion>1</MajorVersion>
   <MinorVersion>0</MinorVersion>
   <PatchVersion>0</PatchVersion>
   <PreReleaseLabel></PreReleaseLabel> <!-- Use 'alpha', 'beta', 'rc.1' or leave empty -->
   ```

2. **Update this CHANGELOG.md** with new version information

3. **Run the build and publish script**:

   ```bash
   .\update-version.ps1 -NewVersion "1.1.0"
   ```

### Version Number Guidelines

- **Major Version**: Breaking changes, incompatible API changes
- **Minor Version**: New features, backward compatible
- **Patch Version**: Bug fixes, backward compatible
- **Pre-release**: Use for alpha, beta, or release candidates

### Examples

- `1.0.0` - Stable release
- `1.1.0-alpha` - Alpha pre-release
- `1.1.0-beta.2` - Second beta release
- `1.1.0-rc.1` - Release candidate
